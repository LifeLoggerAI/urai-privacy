# Version-bound Privacy deletion execution

A stored account-deletion approval previously named Firestore targets by ID and owner only. A correction or replacement with the same ID and owner could therefore be removed, and an administrative token, request, fence, attempt or lease could change while an awaited operation continued.

The v2 dry-run plan now hashes each observed Firestore update time and the current Firebase Auth account creation identity. Destructive Firestore transactions reread the live operation, permanent subject fence, exact attempt, original lease, legal holds and approved plan, then validate the current revocation-checked token and provider-side administrative role after awaited target reads. Each delete also carries the observed update-time precondition. Physical Storage deletes retain immutable generation preconditions and check live execution before and after their waits. Auth identity is checked again after Storage waits. Completion and failure updates cannot overwrite a cancelled, reassigned or superseding operation.

The canonical deployed callable surface remains `functions-entry.ts` through `deletion-mutation-guard.ts`. Existing residual verification remains the only final-completion writer. Legacy plan artifacts that lack version authority fail closed and need a new governed dry run; they are not silently upgraded. Interrupted Storage deletion can resume against the same unchanged approved versions.

Bounded validation: 24 actual handler cases with explicit local SDK/test adapters passed. On unchanged parent source, 16 new refusal cases failed; the seven retained cases and ordinary interrupted-Storage retry passed. Strict changed-module compilation passed against TypeScript 5.9.3 and the actual Firebase Admin 13.10.0, Functions 6.6.0, Firestore 7.11.6 and Storage 7.21.0 declarations. The local Node 24 runtime and Node 22.19.17 declaration package are supplemental evidence. The full frozen Functions installation could not finish because the exact locked `undici-types@7.24.6` tarball was not cached; full declared-Node/native Vitest/emulator evidence is still required.

This is source and adapter proof. It does not establish a loaded Functions worker, cloud deletion, downstream provider erasure, independent acceptance, deployment or Golden Master. Firebase Auth does not expose an atomic version precondition on `deleteUser`; account recreation by privileged actors must respect the permanent deletion fence. The creation-identity checks deny observed replacement, but do not prove safety against an uncontrolled privileged recreation inside the Auth deletion RPC. Already delivered or copied bytes cannot be recalled by these source changes.
